# 開發日誌

保全排班工具的完整開發歷程，記錄每個決策背後的思考脈絡。

---

## 背景

司法院的保全人員每個月用 Excel 手工排班，要同時兼顧：連續上班天數、哨點輪替、假日星期交替、時數平衡⋯⋯光是規則就有六條，容易出錯，也很耗時。

這個 project 的目標不只是「解決問題」，也是用來展示 PM 怎麼跟 AI 協作開發產品。

---

## 第一階段：定義規格

在寫任何 code 之前，先把業務規則整理清楚：

**人員與哨點**
- 6 名保全
- 7 個哨點：平日 A/B/C（10h）、D/E（12h），假日 F/G（12h）
- 每天平日派 5 人（A~E），假日派 2 人（F/G）

**排班規則（6 條）**
1. 不超過連續 6 天上班
2. 同一哨點不連兩天
3. 假日班要六↔日交替（不能連兩個六或連兩個日）
4. 假日哨點 F↔G 交替
5. 每人月總時數差距 ≤ 12h
6. 每個哨點分配次數差距 ≤ 1

這些規則是從實際操作中提煉的，不是憑空設計的。定義清楚規格，才能讓 AI 生出有意義的演算法，而不是亂猜。

## 第二階段：技術選型

**決策：純前端 + localStorage**

考慮過加後端，但這是單人使用的工具，加後端只是增加維護成本。localStorage 完全夠用，備份用匯出/匯入 JSON 解決。

**技術棧**：React 19 + TypeScript + Vite + Tailwind CSS v4

## 第三階段：排班演算法

這是整個 project 最複雜的部分，也經歷了最多迭代。

### v1：Greedy（貪婪法）

最初的演算法是簡單的貪婪：每天逐一分配哨點，給當前「最需要」的人。

**問題**：貪婪法只看當下，不看全局。某人今天搶到高時數哨點，之後反而更難平衡。月底時數差距高達 20~34h，遠超 12h 的規格。

### v2：Quota-based + 回溯（Backtracking）

重新設計成兩個 Phase：

**Phase 1（預算配額）**

預先計算每人每個哨點「目標應排幾次」，用數學保證整體公平：
- 每個哨點基礎配額 = ⌊總天數 / 人數⌋
- 多餘名額按時數由高到低分配，全局最小化時數方差

**Phase 2（逐日排班）**

用「緊迫度分數」驅動每天的排班決策：

```
urgency(人, 哨點) = 剩餘配額 - 目標配額 × (剩餘天數 / 總天數)
```

正值 = 落後進度（優先排），負值 = 超前進度（可晚排）。

每天用**回溯搜尋**窮舉所有可能組合（最多 P(6,5)=720 種），選出全局最優的當日指派。比貪婪法更可靠。

**問題**：時數差距縮小了，但某幾個月（1、6、7、8、12 月）仍然偏高。

### v3：修正時數修正權重

找到根本原因：Phase 2 的時數偏差修正項權重太小（0.5），導致修正力道不夠。

```
score = urgency × 10 + 班次虧欠 × 3 + 規則懲罰 - 時數偏差 × 2.0
```

把權重從 0.5 提高到 **2.0**，同時跑 **20 次**取時數差最小的結果。

效果：6 月從 34h 差距降到 0h（完美平衡），所有月份 ≤ 12h。

**關鍵洞察**：Phase 1 算出來的目標時數差最多只有 10h，修正項要有足夠的影響力才能傳遞到 Phase 2。權重 0.5 時修正力只有 5 分，被 urgency 的 10 分輕易覆蓋。

### v4：完整重寫為 CSP Backtracking（對齊 Python 版本品質）

起因：使用者用 Codex 根據規格生了一個 Python 版本（`guard-scheduler-sideproject/`），拿來對比發現 Python 版本的排班品質更好——硬違規 0，軟目標幾乎全部月份達標。分析根本差異後，完整重寫排班演算法。

**架構重新設計**

從「逐日最優貪婪」改為「隨機重啟 + 日內 CSP 回溯」：

```
generateSchedule(月份) {
  Phase 1：calcTargetCounts — 預算配額（逐哨點順序 + 時數排序分配餘數）
  Phase 2：for (1000 次 attempts) {
    attemptSchedule — 逐日用 CSP backtracking 排班
    evaluateAttempt — 計算品質向量
    if (isBetter) 更新最佳解
    if (完美解) 提前結束
  }
}
```

**五個關鍵修正（與 Python 版本對齊）**

1. **時數均衡權重**：`hourGap` 係數 0.1 → 0.8（Python 就是 0.8）
2. **動態 most-constrained-first**：每層遞迴重算各哨點的剩餘候選數，每次先排最緊縮的哨點（對齊 Python 的 `choose_next_post`）
3. **配額 deficit 允許負值**：超過配額者 deficit 變負數 = 扣分，防止壟斷
4. **extras 逐哨點依序分配**：Phase 1 對每個哨點單獨排序並分配餘數，每次都根據「當下累積預估時數」排序（對齊 Python 的 `_build_targets`）
5. **目標函數**：用 `postExcessSum`（∑ max(0, spread-1)）取代 `postSpreadMax`，對齊 Python 的四層字典序目標：`(hours_excess, post_excess, hours_spread, post_sum)`

**benchmark 結果（2026 全年，seed=12345，1000 attempts）**

| 月份 | 硬違規 | 時數區間 | ≤12h | 哨點 max | ≤1 |
|------|--------|----------|------|----------|----|
| 全部 12 個月 | **0** | 4h~12h | ✓ 12/12 | 1 | ✓ 12/12 |

**UI 新增：規則實際數據**

規則檢查區塊每條規則下方顯示本月實際統計：
- 本月最長連續上班 N 天
- 連續同哨點 N 次，共檢查 M 組相鄰上班日
- 假日星期/哨點未交替 N 次，共檢查 M 次
- 工時差距 N 小時（最高 X、最低 Y）
- 最大哨點分配差距 N 班

**預設 attempts 從 100 → 1000**

原因：100 次在困難月份（如 2026-06 端午跨週五）有 60% 機率卡在局部最優，1000 次降至約 5%，且每次執行約 40~200ms，UI 仍即時響應。

## 第五階段：功能迭代

### 功能一：規則驗證視覺化

排班人員需要知道「這張班表有沒有問題」。

做法：
- 違規格子標紅，hover 顯示原因
- 底部「規則檢查」區塊列出所有違規筆數
- 班別統計表讓每人的哨點分配一目了然

### 功能二：颱風假

**規格**：颱風日 → 取消 A/B/C，D/E 的人改去 F/G。

**踩到的 bug**：假日本來就沒有 A~E，對假日套用颱風邏輯會把所有人都設成休假。

**修正**：颱風假只適用平日，假日顯示「不適用」。

**UX 三次迭代**：
1. 點日期標題 → 彈出選單（太隱藏）
2. 每欄加颱風按鈕（欄位太多、畫面雜亂）
3. **最終版**：toolbar 單一「颱風假」按鈕 → 月曆選日 modal

月曆 modal 的邏輯：
- 假日/週末自動灰掉（不可點）
- 點平日 → 選中（amber 高亮）+ 顯示影響說明
- 已設定颱風的日期顯示紅色，點擊可取消
- 移除 emoji icon，改純文字按鈕

**設計決策**：「很少用的功能要讓它顯眼，不然放在隱藏選單裡沒人找得到」。

### 功能三：請假換班

**原始想法**：點格子 → 選「休」就好。

**問題**：直接把人設成休假會讓那天少一個哨點，不符合現實。現實中換班是「借班再還班」。

**重新設計**：兩步驟流程

**Step 1 選換班對象**
- 找出當天休息的人（才有辦法幫你上班）
- 驗證換進來不違反規則 1&2

**Step 2 選還班日**
- 找出之後的日子：你休息、對方有班、你接進去不違規
- 限制：只能換**同時數**的班（A/B/C↔A/B/C，D/E/F/G↔D/E/F/G）

**思考過程**：
- 一開始限制「同哨點」→ 太死板
- 改「同類型」（weekday/holiday）→ 還是太限制，D 只能換 E
- 最終「同時數」→ 最符合現實，12h 的人可以跨類型互換

**另一個決策**：有班的格子不顯示「休」按鈕，避免讓排班人員直接清空哨點。

## 第六階段：部署

**GitHub Pages vs Vercel**：選 Vercel。

原因：Vite SPA 在 GitHub Pages 需要額外設定 base path 和 404 redirect，Vercel 是 Vite 一等公民，零設定。

**小插曲**：`guard-scheduler.vercel.app` 被別人的同題目專案（Next.js 英文版）佔走了，改用 `basil-guard-scheduler.vercel.app`。

**資料存哪？**：localStorage。人員和哨點的預設值寫死在 `store.ts`，第一次開啟自動帶入，不需要後端。判斷標準：單一使用者、資料幾乎不變、使用者本來就在改 code → 寫死完全合理。

## 回顧

**AI 協作的幾個觀察**：

1. **規格定義不能省**：把六條規則整理清楚，AI 才能生出有意義的演算法。含糊的需求只會得到含糊的實作。

2. **AI 的第一版通常要推翻**：UI 第一版太保守、換班邏輯第一版太簡化、演算法第一版時數差太大。要有能力判斷輸出品質，才能有效迭代。

3. **方向要自己定**：每次功能設計（要不要加驗證？颱風假 UX 要怎麼放？換班邏輯要怎麼定義合法？）都是 PM 在做決策，AI 在執行。

4. **Debug 需要懂原理**：時數差距問題找了很久，最後要理解演算法的數學才能找到根本原因（權重不夠）。不是每個問題 AI 都能自己找到。
